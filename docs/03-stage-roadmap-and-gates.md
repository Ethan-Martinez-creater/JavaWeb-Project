# 分阶段开发计划、审核门禁与交接协议

**所有阶段都以 PR 为验收单位。每阶段 Codex 自主完成该阶段全部任务、测试和文档后，才请求集中审核。未经明确审核通过，不得推进下一阶段。**

## Stage 0 — 一次性环境盘点（已评估通过并合并，PR #1）

- 只允许执行 docs/06-environment-preflight.md 中的**只读检查**，不安装/升级、不启动服务、不下载镜像、不写业务代码。
- 报告检查位置、当前版本和可用性，不推断 Codex 环境就是用户本地环境。
- 用小型 preflight PR 留档；这**不构成 Stage 1 的代码审查**。
- 2026-10-20 已基于 PR #1 和官方兼容性资料完成审查；结果见 docs/07-stage-0-review-and-stage-1-authorization.md。PR #1 已合并，可基于最新 main 开发 Stage 1。
- 后续 Stage 1–4 的「每阶段结束一次代码审核」机制不变。

## Stage 1 — 工程骨架、认证权限、活动基础域（Stage 0 PR #1 合并后已授权启动）

- 交付：Spring Boot + MyBatis + MySQL + Flyway + Maven Wrapper；模块化单体规范结构；注册/登录/JWT/RBAC；活动、场次、票种、发布与公开浏览 REST API；Docker MySQL；测试与 CI。
- 不交付：订单、库存扣减、支付、核销、Redis、MQ、前端。
- Gate：干净环境构建通过，MySQL 真实集成测试通过，鉴权/所有权与草稿不可见测试通过，契约匹配，日志/密钥安全，无重大结构问题。
- 详见 docs/04-stage-1-codex-task.md。

## Stage 2 — 票务预约、库存与订单履约闭环（未授权）

- 交付：预约下单、库存原子预占/释放、幂等、订单状态机、模拟支付、电子票核销；关键竞态和并发用例。
- Gate：对给定 SKU 库存 100、1000 个不同用户并发预约的测试成功数 ≤100 且库存不为负；同一幂等键不会产生双订单；重复关单与支付竞态不造成状态或库存错误；核销仅成功一次；事务/索引设计有证据。
- 依赖：Stage 1 完成并合并通过的 PR。
- 不引入 Redis/MQ；先依赖 MySQL 正确性闭环。

## Stage 3 — Redis 缓存、RabbitMQ 消息可靠性（未授权）

- 交付：活动缓存与缓存失效、适度限流；订单到期消息、异步通知、持久化 Outbox/可靠发布、幂等消费、失败恢复与定时补偿；相关容器配置。
- Gate：容器环境下模拟重复投递/消费者重启/消息延迟或缺失，订单不重复释放，超时订单最终能关闭；数据库库存与状态满足不变量；明确缓存一致性边界和故障流程。
- 依赖：Stage 2 审核通过。

## Stage 4 — Vue 演示、完整部署、性能验证与面试材料（未授权）

- 交付：Vue 3 + TypeScript + Element Plus 精简用户端/运营端；Docker Compose 完整启动；OpenAPI/README；API 自动测试与性能基准；最终架构图、知识点索引、关键类/调用链、可复现实验步骤、简历技术亮点的证据链接。
- Gate：新环境按 README 启动并完成端到端演示；关键测试/CI 全绿；所述性能指标附命令、硬件/环境、原始结果；面试文档每项均可指到代码与测试。
- 依赖：Stage 3 审核通过。

## 必须遵守的 PR 流程

1. Stage 0 PR #1 合并、版本确认后，Codex 从 main 最新代码切出 codex/stage-N-* 分支，**正式开发第一轮只实现 Stage 1**。
2. 在分支上进行所有实现、格式化、测试和必要文档更新；不得提交 .env、密码、令牌或大体积构建产物。
3. 完成 docs/handoffs/stage-N.md 交接报告，并创建 PR：标题格式 [Stage N] 主题。
4. PR 中列出验收条款的完成状态、关键提交 SHA、测试环境和实测命令结果、已知风险、不在范围的事项；提供主要源码/测试路径。
5. Codex 向用户交付 PR 链接和简短结果；**停止，不得自己合并或继续 Stage N+1**。
6. ChatGPT 集中审查 PR diff、关键源码、迁移、测试和 CI；给出 ACCEPT / FIX / BLOCKED 结论。若 FIX，由 Codex 在同一分支修复并更新交接报告；阶段结束再次审核。
7. 用户已授权 ChatGPT 代为执行 GitHub 操作：**审核结论为 ACCEPT 时，由 ChatGPT 直接合并 PR、更新任务书、通知用户并授权下一阶段**；如为 FIX/BLOCKED，不合并且不推进。涉及重大需求/技术基线调整或系统级安装修改时仍需用户确认。

## 审核严重度

- P0（阻断）：越权、安全漏洞、数据错误/超卖、构建不可用、隐瞒失败、跨阶段开发、重大不可维护架构。
- P1（须修复）：重要逻辑缺陷、关键测试缺失、错误处理不可靠、迁移不可复现、契约明显偏离。
- P2（可记录）：命名、文档措辞、可读性小改进和非必要扩展。

若 CI 未运行、测试环境不可用或外部限制导致无法验证，状态必须写 UNVERIFIED；不能自动评为通过。

## 时间与节奏

按功能阶段（非固定天数）验收，以减少频繁审核。范围发生冲突时先保证可运行、正确性、安全与测试，再删减次要 UI/报表；不得为了赶进度跳过 Gate。
