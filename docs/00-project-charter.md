# EventFlow 项目章程（v1，2026-10-20）

## 1. 项目目标

这是一个求职演示型 Java Web 系统。新增项目应与已有 Python/FastAPI/Agent 项目形成技术互补，主要展示：
- Java/Spring 业务分层、依赖注入、Spring Security、MyBatis SQL、MySQL 事务与索引；
- 有状态订单、库存防超卖、幂等、订单/核销并发安全；
- Redis 缓存与流量控制、RabbitMQ 异步/可靠性及失败恢复；
- 测试、CI、数据库迁移、Docker 部署、完整的技术设计与面试解说。

产品价值与工程演示优先于堆功能。所有亮点都要能定位到源码、测试与可复现的证据。

## 2. 用户与业务

角色：USER（报名/预约）、ORGANIZER（管理自己创建的活动）、ADMIN（系统维护，可延期实现）。
主流程：主办方创建活动 → 创建场次与票种 → 发布 → 用户浏览 → 预约下单并预占票量 → 模拟支付 → 生成电子票 → 入场时核销；未支付订单到期后关闭并释放预占。

项目不接第三方支付，不存储真实资金/卡信息。模拟支付应保留真实状态流转和并发约束，不伪装为生产支付解决方案。

## 3. 范围控制

### 必需
- REST API、JWT 身份认证、角色/资源级授权
- 活动、场次、票种和库存、订单、模拟支付、核销
- MySQL 持久化及迁移；订单/库存事务完整性
- Redis、RabbitMQ 的有理由的使用场景
- 自动化测试、基础 CI、运行文档与复现脚本
- 简洁的 Vue 3 用户与运营演示页（最终阶段）

### 不做
- Spring Cloud 微服务拆分、分布式事务中间件、K8s、复杂多租户
- 真实支付/退款、财务对账、实名验票、短信/邮件真实网关
- 复杂购物车、优惠券、会员、推荐系统
- 早期阶段为了简历关键词引入无明确需求的中间件
- 未经实测的 QPS/性能提升声明

## 4. 非功能要求

- 首先保证正确性，再优化性能；防超卖、幂等、防越权属于 P0。
- 可以在普通开发机使用 Docker Compose 复现依赖环境。
- API 错误、HTTP 状态码与日志具备诊断能力，但绝不能泄露敏感数据。
- 数据库时间统一保存 UTC；前端按当地时区展示。
- 记录关键设计取舍，便于学习复盘。
- 严禁仓库内保存生产密钥、真实凭据或不可公开数据。

## 5. 分工与决策

- 用户：确定产品目标与项目授权；已授权 ChatGPT 代理执行阶段通过后的 GitHub PR 合并与相关仓库维护，无需逐次手动点击。重大范围/技术方向变更及需要系统级安装修改仍需用户批准。
- Codex：按当前阶段规范独立实现、执行测试、形成 PR、提交交接报告。
- ChatGPT：仅在阶段结束时集中审查代码、架构、安全、测试及验收证据，形成 ACCEPT / FIX / BLOCKED 结论；ACCEPT 后由 ChatGPT 合并阶段 PR、更新文档并发布下一阶段任务，告知用户结果。
- main：每轮已确认的基线。编码必须走阶段分支与 PR；Codex 不得合并，ChatGPT 只能在阶段审核 ACCEPT 后合并。
- 若发现影响阶段成败的冲突，Codex 记录原因与可行方案于交接报告，而不是绕过约束。

## 6. 完成定义

最终项目必须能运行演示、能复现关键并发/异常场景，并产生按源码定位的面试学习文档。基础 CRUD 数量不作为完成标准。
